Commands for rerunning the checks are under [Reproducing the checks](#reproducing-the-checks). Each entry states its own environment and limits. A unit test, fixture or preview is not proof of a completed adventure playtest.

## 2026-10-28 — Foundry 14.369 compatibility

Foundry **14.369** (Stable 11, 8 October 2026) is the newest core release; its notes list no breaking changes or deprecations. A source audit found no removed or deprecated core APIs: chat hooks use `renderChatMessageHTML`, dialogs use `DialogV2`, scene controls use the v13+ record shape and sheets use ApplicationV2. The 0.4.2 runtime files are unchanged since the `v0.4.2` tag. An archive built from them passed the full native journey in licensed standalone Foundry 14.369 with zero modules: 14 onboarding checks, the alpha-play GM/player workflow, and all 55 `--features` checks. The run recorded no page errors and no core compatibility (deprecation) warnings from system or harness code. The packaged fresh-install recovery scenario also passed on 14.369: all actor types, damage 2 → 5 → undo 2, and persistence after reload, with no page errors or compatibility warnings. The published release ZIP itself was not reinstalled for these checks. `system.json` now declares `verified: "14.369"` for the next release.

14.369 required harness-only changes. The join screen now picks users from a `<select>`. World data now includes invitation links, which core reads from an address lookup that finishes a few seconds after the server starts listening; a client loading inside that window fails with a `[ReleaseData] validation errors` page error. The native harnesses now choose users from either form, launch disposable servers with `--noipdiscovery`, retry only that recognized startup race (recording `coreStartupRetries`), read the core version from the installed `package.json`, and fail when system code raises a core compatibility warning. Harness sidebar calls use `Sidebar#changeTab`. On Windows, keep `--output` short: a deep output directory pushed world compendium paths past the path-length limit and failed the three pack-creating features until the run moved to `.local/n`. Dice So Nice, DoR and upgrade-from-baseline scenarios were not repeated on 14.369.

## Reproducing the checks

How to rerun the automated and licensed-Foundry checks recorded above. These commands were moved here from the user guides.

### Browser fixtures

`npm run test:browser` first builds the current package, then runs the repository's `tests/*-ui.mjs` fixtures sequentially with a two-minute bound per fixture. Add `--runs=N --seed=S` to repeat the fixtures in fresh browser processes; `npm run test:playtest` is the three-run tabletop-focused shortcut (see [Headless playtest loop](headless-playtest.md)). A timeout stops that fixture's owned process tree, including its browser descendants; it never kills processes by name. It writes JSON, logs and screenshots under `test-results/browser` (or the selected output path), including any timeout or cleanup failure. CI installs Chromium and uploads these artifacts on success or failure. These are real-browser fixtures, not native Foundry acceptance.

Set `CHROMIUM_PATH` to an installed browser if Playwright's bundled browser is unavailable. The tabletop fixture can also be run directly with `node tests/tabletop-ui.mjs`.

### Accessibility and interaction checks

Run from the repository root:

```sh
node --test tests/motion-preference.test.mjs tests/range-motion.test.mjs tests/sheet-listeners.test.mjs
node tests/accessibility-ui.mjs
node --test tests/*.test.mjs
node scripts/check.mjs
node scripts/build.mjs
```

`TEST_ARTIFACTS_DIR` selects the evidence directory for the accessibility fixture; the default is ignored `.local/accessibility`.

### Native onboarding, play and feature harness

`scripts/onboarding-acceptance.mjs` is an opt-in licensed native journey. It creates a fresh disposable world and data directory on an isolated port, installs the built archive, copies a supplied private licence without printing it, and stops only its owned server/browser. It never uses shared port 30002. Run with `--foundry-app=<main.js> --license=<private-license.json> --port=<isolated-port>`. Screenshots and native results remain under ignored `.local/onboarding-native/`. The world records the core version read from the installed Foundry `package.json`; `--core-version=<build>` overrides it. Results list core compatibility warnings, and the run fails if system code raised any.

For the 0.4.2 Beta, add `--alpha-play` to exercise a separate owned player character through manual creation, skills and XP, starting equipment/funds, Ready for play, a narrative roll, GM-reviewed damage/undo/recovery, session awards and skill advancement with reload persistence. This automation uses actual native dialogs; APIs seed the disposable world and open documents. The independent human-GM gate in the [Foundry listing record](foundry-listing.md) remains separate.

Add `--features` for the onboarding/play journey followed by the broader native feature sweep. `--features-only` runs the sweep after the required initial core-tour handover and explicit GM authority selection; `--feature-filter=<regular-expression>` selects diagnostic checks and reports every skipped check. Each result records whether it used native UI, canvas rendering or document APIs. Failures retain screenshots, DOM and synthetic document state under the selected ignored `--output` directory; no production world is opened. To test an already-installed Dice So Nice copy, combine `--features-only` with `--dice-so-nice=<module-directory>`. The module is copied into the disposable data directory and enabled there only.

### Native upgrade and recovery harness

The opt-in native harness requires a locally licensed Foundry installation, its private license file and package ZIPs. Build/audit the candidate first, then run:

```text
npm run build
npm run audit:release
npm run test:recovery -- --foundry-app=<absolute-main.js> --license=<private-license.json> --port=30026 --baseline=<0.2.1-package.zip> --baseline=<0.3.0-package.zip>
```

Use `CHROMIUM_PATH` only when Chromium is installed outside Playwright's cache. Optional arguments are `--archive=<candidate.zip>`, `--output=<private-output-directory>` and `--core-version=<installed-version>` (default: the build in the installed Foundry `package.json`). The harness rejects an occupied port and the shared development port. It creates unique disposable data directories; it never accepts or modifies a live-world path and never overwrites an existing package installation.

For each baseline it creates synthetic actors of all six types, embedded equipment, linked and unlinked tokens, a private journal, a chat entry and a world compendium using that baseline package. It shuts down the world, copies it to a candidate installation, compares preserved values, tests a real effect/undo and reload, then opens a separate restoration using the untouched backup and baseline package. Fresh installation is a separate scenario. It preserves private logs, screenshots, archive hashes and `results.json`, and stops its own server/client processes. No publishing, promotion, runner registration or AtlasMind dispatcher policy is performed by these commands.

### Actor icon audit

`npm run audit:icons` renders every family in Chromium at 64 pixels and measures the actual SVG geometry. It also decodes every SVG as an image to check its intrinsic canvas resolution. It fails for an off-centre character head/body pair, a glyph outside the protected frame area, vehicle tags that miss the ring midpoint or outer edge, undersized image sources, or an unmapped database species or vehicle. The latest machine-readable result is [actor-icon-audit.json](actor-icon-audit.json). See [Actor icons](../guides/actor-icons.md).
